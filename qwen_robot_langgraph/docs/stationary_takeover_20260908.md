## HTTP 400 的证据与修复

旧 `GET /tasks` 明确过滤 `voice:%` 内部播报。旧测试的 `quiet()` 只查看这个列表，并额外等待 1.5 秒；报时任务已 `completed` 时，其结果播报仍可持有 speaker、outbox 为 playing、speech operation 为 accepted。

本轮在未修改应用代码时，提交只读报时请求，复用旧等待条件，再请求录音，实测 HTTP 400，完整正文为：

```json
{"error": "speaker_busy_try_after_playback"}
```

请求约 0.005 秒即被拒绝，未播放状态语音样本，也未进入录音。这证实了该路径的内部播报竞争。历史那一次失败没有响应正文，不能反向证明它唯一可能的原因，更不能将它判作 ASR 识别失败。

本轮代码变更：

- 新增 `/audio-status`，统计全局音频锁、待播报及执行中播报，覆盖隐藏播报和其他会话，不暴露其他会话内容。
- 两个原地 API 复测脚本使用全局音频就绪状态；失败保存 HTTP 状态码、正文和路径，等待超时保存状态诊断。
- `/voice-turn` 原子检查并占用 microphone 与 speaker，使用每请求独立的资源所有者，避免录音中启动新播报、并发同 request_id 误共享资源。异常路径释放两项资源。
- 保留 busy 拒绝行为和 unknown 资源占用；不通过取消播报、重发动作或强制清锁“修好”测试。
- 应用启动依据持久操作结果修复历史内部播报状态。实机 8 条旧 running 已按已完成操作记录恢复为 completed；没有重播。缺失或不确定结果仍标 unknown 并保留已有锁。

交接前已完成的 JSON 严格解析、有限规范化、确定性参数规则、否定与歧义校验、录音缓冲调整等修改也保留在本次提交中。
